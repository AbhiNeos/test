Shared Flow Architecture And Policies Covered

1. Overview

The Shared Flow architecture establishes a reusable and structured approach to implementing common functionality across API proxies in Apigee.

It promotes consistency, reusability, and maintainability by organizing shared logic into modular components that can be applied uniformly across APIs. It also ensures a clear separation between reusable platform capabilities and API-specific implementations.

This standard serves as a foundation for designing scalable and governable API solutions.

2. Shared Flow → Apigee Policy Mapping

1. SF-PreFlightCheck

Purpose:

Performs initial sanity validation before any heavy processing begins. Ensures required headers, query params, and basic request structure are present and valid. Also loads environment-specific configurations (KVM) and initializes variables required for downstream flows.

Apigee Policies:

  • JavaScript
  • KeyValueMapOperations
2. SF-AuthValidation

Purpose:

Enforces all standard authentication and security controls in a centralized manner. Validates client identity using OAuth tokens, or basic authentication. Acts as the primary security gate before further processing.

Apigee Policies:

  • Verify JWT
  • Basic Auth
  • Api Key Validation
3. SF-SecurityFilters

Purpose:

Enforces all standard security controls in a centralized manner, protects APIs against common threats like malicious payloads or injection attacks. Acts as the primary security gate before further processing.

Apigee Policies:

  • JSONThreatProtection
  • XMLThreatProtection
  • RegularExpressionProtection
  • CORS
4. SF-DecryptRequestPayload

Purpose:

Decrypts the incoming encrypted request payload before further processing. Uses KMS-backed keys to securely handle encrypted data from consumer applications, making the decrypted content available for schema validation and downstream flows.

Apigee Policies:

  • JavaScript (Decryption logic)
  • ServiceCallout (KMS integration)
  • AssignMessage
5. OAS Validation Policy

Purpose:

Ensures that incoming requests strictly adhere to defined API contracts such as OpenAPI or JSON/XML schemas. This prevents malformed or unexpected payloads from reaching backend systems and enforces strong contract governance across all APIs.

Apigee Policies:

  • OAS Validation
  • JSON Schema Validation
6. SF-TrafficManagement

Purpose:

Controls the volume of API traffic to protect backend services from overload. Enforces rate limits, quotas, and spike arrest policies per consumer or application to ensure fair usage and platform stability.

Apigee Policies:

  • SpikeArrest
  • Quota
  • ConcurrentRateLimit
7. SF-TokenExchange

Purpose:

Exchanges the consumer-facing access token for a backend-compatible token. Decouples consumer authentication from backend service authentication, enabling secure service-to-service communication with proper identity propagation.

Apigee Policies:

  • ServiceCallout (Token endpoint)
  • AssignMessage
  • ExtractVariables
8. SF-HeaderInjection

Purpose:

Injects or modifies HTTP headers before forwarding the request to the backend. Adds correlation IDs, trace headers, internal routing metadata, and any backend-required custom headers for proper request tracking and processing.

Apigee Policies:

  • AssignMessage
  • JavaScript
9. SF-SetTargetURL

Purpose:

Dynamically resolves and sets the target backend URL based on environment, KVM lookups, or request context. Enables flexible routing to different backend endpoints without modifying the proxy configuration.

Apigee Policies:

  • KeyValueMapOperations
  • AssignMessage (target.url)
  • JavaScript
10. SF-CommonLogging

Purpose:

Provides centralized logging for all API transactions. Captures request/response metadata, timestamps, consumer details, and performance metrics. Sends log data to external logging platforms for monitoring, analytics, and audit compliance.

Apigee Policies:

  • MessageLogging
  • JavaScript (log formatting)
  • FlowCallout
11. SF-EncryptResponsePayload

Purpose:

Encrypts the response payload before sending it back to the consumer. Ensures sensitive data in transit is protected end-to-end using KMS-backed encryption keys.

Apigee Policies:

  • JavaScript (Encryption logic)
  • ServiceCallout (KMS integration)
  • AssignMessage
12. SF-ErrorHandling

Purpose:

Provides centralized fault handling across all proxy flows. Catches uncaught exceptions, maps backend error codes to consumer-friendly messages, and returns a consistent error response format with proper HTTP status codes.

Apigee Policies:

  • RaiseFault
  • AssignMessage
  • JavaScript (error mapping)

3. Flow Execution Order

Request Flow:

Consumer → SF-CommonLogging → SF-PreFlightCheck → SF-AuthValidation → SF-DecryptRequestPayload → OAS Validation → SF-SecurityFilters → SF-TrafficManagement → SF-TokenExchange → SF-HeaderInjection → SF-SetTargetURL → Backend

Response Flow:

Backend → SF-ErrorHandling → SF-HeaderInjection → SF-EncryptResponsePayload → SF-CommonLogging → Consumer

Fault Flow:

Any Error → SF-ErrorHandling → SF-CommonLogging → Consumer (standardized error response)
